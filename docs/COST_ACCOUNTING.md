# COST ACCOUNTING — RECONCILED, EVERY NUMBER WITH A UNIT

Generated by `docs/audit/accounting_ledger.mjs` (CODE-DERIVED constants) plus the
published state (**MEASURED**). Units are never mixed: *request* = one external
`fetch()`; *op* = one symbol-refresh; *row* = one candle row transmitted;
*upsert* = one row written at the destination; *D1 read* = one row counted by D1.

---

## 1. 138 or 139 — the missing request

Neither figure was a rounding. The table had four lines and I quoted the sum of
all four while listing three: archive 30 + live 27 + mirror 81 + **`archiveId`
cache refresh 1** = 139. But the mirror figure itself was wrong (§9), so the
correct arithmetic is:

```
external requests demanded by one intraday cron invocation
  = SHARD x archive_cost            = 6 x 5 = 30
  + tracked                          = 27 x 1 = 27
  + changed_tracked x mirror_cost    = 27 x 1 = 27
  + archiveId cache refresh          =          1
  = 85 requests, against a 50 limit (170%)
```

## 2. Does an archive symbol cost 5 or 6?

`archiveId` **does** issue HTTP — but not usually. It holds a module-level map
with a 5-minute TTL (`ARCHIVE_ID_TTL`), so within one isolate it is a cache hit
for all 6 symbols of a shard and for the next several minutes.

| case | requests | when |
|---|---|---|
| **minimum / typical** | **5** | id cache warm: Yahoo 1 + POST 2 + count 1 + PATCH 1 |
| cold id cache | 6 | first shard after an isolate start or after 5 minutes |
| unknown symbol | 8 | id miss → re-list → POST create → re-list |

The POST count is `ceil(bars/1000)`; a 5-day pull is ~1,950 bars → 2.

## 3. 19.7 or 23.4 — the universe is 119, not 100

`universeList` = `ARCHIVE_UNIVERSE` (100 fixed symbols) **+ `universe_extra`**.
**MEASURED** in the published coverage: **119 universe entries**.
2,340 ops/day ÷ 119 symbols = **19.7 refreshes per symbol per day**. With the
fixed 100 only it would be 23.4; the extra 19 symbols are real.
The shard runs once per cron minute while the market is open: 390 runs/day.

## 7. The two promises — what actually orders the requests

```
scheduledRun
  ├─ await quota / market / trackedSymbols        (bindings only)
  ├─ ctx.waitUntil(archiveShardIIFE())   <- line 3268, starts executing at once
  ├─ ctx.waitUntil(syncMany(...).then(mirrorFlush).then(log))  <- line 3297
  └─ return                                       (invocation stays alive)
```
A possible interleaving:
```
archive: universeList (binding) -> Yahoo(UNH) ....
live:                               Yahoo(AAPL) -> D1 batch -> D1 batch
archive: POST chunk 1 -> POST chunk 2 -> count -> PATCH
live:                               Yahoo(AMD) -> ...
```
**There is no ordering guarantee.** Whichever promise resolves its current
`await` first issues the next request; the runtime decides. That is why the wall
moves between symbols #15 and #19 from minute to minute.

## 8. Failure-point range

Requests consumed by the archive side before the live loop can finish:

| case | archive cost | tracked symbols reachable | wall at |
|---|---|---|---|
| best (id warm, 1 POST chunk) | 24 | 26 | #27 |
| typical (id warm, 2 chunks) | 30 | 19 | **#20** |
| worst (id cold, new symbol) | 36 | 12 | #13 |

**MEASURED wall:** #15 rarely, #16 often, #18+ always — inside this range and
close to the typical case.

## 9. Mirror cost — correction: **1 request per symbol, not 3**

`mirrorBars` (CODE-DERIVED, lines 610–631) performs **exactly one** call:
`POST /rest/v1/bars?on_conflict=symbol,unix` with **all rows in one body**, no
chunking, no count, no PATCH. So:
- once **per symbol**, not per batch;
- only when `changes > 0` (the queue is only pushed then);
- all of them **after** the whole `syncMany` loop, in its `.then()`.

If 27 symbols changed in one minute: 27 POSTs, all after the loop — which in
practice is after the budget is already gone.

My earlier "81 requests" was wrong; it applied `archiveWrite`'s cost to
`mirrorBars`. The corrected demand is 85 requests, not 139.

## 10. The mirror table — absolute writer/reader list

**Writers →** `mirrorBars` (line 623). That is all.

**Readers ←**
| route | what it does with the result |
|---|---|
| `/mirror/:sym[/:date]` | returns the rows as JSON to the caller. No page uses it; it is not referenced by any HTML in the repo |
| `/selfcheck` | `mirrorRead('SPY', null, 1)` → prints `ok, reachable` or `FAILED: …`. Only the reachability matters, not the data |
| `/mirror/compare` | per symbol, `count=exact` against `bars` and compares totals with D1's `days` — returns counts only |

**Is any production feature's output dependent on this table? No.** No screen,
export, copy, chart, Trader path or publish reads it. It is written at 1 request
per changed symbol per sync and consumed only by three diagnostics.

## 12. The same candle in three stores — **UNKNOWN as a measurement**

by design, and `bars` is a snapshot of whatever D1 held at mirror time.

## 13 + 14. Cursor loop and mirror loss — CODE-PROVEN / RUNTIME-NOT-MEASURED

Both mechanisms are proven from source:
- the cursor advances only after the shard loop completes;
- `mirrorQueue` is flushed only after the whole `syncMany` loop, is module state,
  and a minute already stored yields `changes = 0` on the next run, so it is
  never re-queued.

Neither has an observed instance in what is published: the event log covers a
weekend (2026-09-20 → 09-21), and `archive_intraday_partial` events only appear
on failure during a session. **Status: CODE-PROVEN, RUNTIME-NOT-MEASURED.**
